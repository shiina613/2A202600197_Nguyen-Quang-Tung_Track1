# Decision Logging Instructions

## Goal
Maintain a living decision log in `logging.md` that captures:
- The question/problem being solved
- Options considered and evaluated
- The decision made
- Actions taken as a result
- Impact on the submission files

This creates a transparent trail of thinking for Day 16-17 brainstorm and makes it easy to explain "why this, not that" to reviewers.

## When to Update logging.md

Update the log **immediately** after any of these events:

1. **Major decision point resolved**
   - Example: Choosing primary KPI, defining buyer/user split, selecting value proposition

2. **Approach rejected with clear reasoning**
   - Example: Explain-back metric rejected due to UX friction

3. **Action completed and tracked**
   - Example: Created submission_final.md, added metric definitions

4. **Assumption clarified or validated**
   - Example: "Parents care more about results than learning process"

## Format Template

When adding to logging.md, use this structure:

```markdown
## Decision #[N]: [Short title of decision]

**Question:** [What problem are we solving?]

**Options considered:**
1. [Option A] - [brief eval]
2. [Option B] - [brief eval]
3. [Option C] - [brief eval]

**Decision:** [Which one we chose and why in 1-2 sentences]

**Action taken:** [What we did as a result]

**Impact on day16:** [How this changes the submission]
```

## Agent Behavior

At the end of each brainstorm exchange:
1. If a decision was made → Offer to add it to logging.md
2. If an approach was rejected → Ask "Should I log this rejection?" 
3. Summarize what changed in the submission files

Do **not** wait for the user to ask. Be proactive: "I think this decision should go in logging.md. Should I add it?"

## File Locations

- Decision log: `logging.md` (root of project)
- Affected submissions: `day16/submission_final.md`, `day17/submission.md` (if applicable)
- Supporting context: Keep this instruction nearby for reference
