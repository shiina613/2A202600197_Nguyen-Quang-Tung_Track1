Bài 2 — Ba lớp giải pháp (chi tiết)

Ánh xạ worksheet 1-map-and-format.md: RC-1 ↔ Lớp 3, RC-2 ↔ Lớp 2, RC-3 ↔ Lớp 1. Một lớp lọt vẫn còn hai lớp kia.

Lớp 1 · UI/UX (RC-3)
  • Thẻ confirm entity giữa chat và DB; trạng thái mặc định draft.
  • Badge 🟢 / 🟡 / 🔴: “đủ rõ” vs “AI đoán / cần hỏi” vs “chặn / bắt xác nhận”.
  • Giao dịch lớn / ambiguous: thêm bước (gõ chữ, checkbox) trước Lưu.
  • File tham chiếu: artifact/1-uiux/card.md, demo.md.
Lớp 2 · Prompt (RC-2)
  • System prompt bắt schema MoneyEntityV1 + sum_locked, needs_user_confirm.
  • Luật: lóng (“cành”, “củ”, “lít”, “rưỡi”) → hạ confidence, bắt hỏi lại trong user_text.
  • Cấm ngôn ngữ “đã lưu” khi chưa có sự kiện commit từ backend.
  • File: artifact/2-prompt/card.md, demo.md.
Lớp 3 · Kiến trúc (RC-1)
  • Dictionary / rule store quy đổi lóng (phiên bản hóa, có log thay đổi).
  • Sanity theo category (min/max, outlier) — tách khỏi LLM.
  • Commit chỉ qua API có request_id, checksum tổng, audit entity_decisions.
  • File: artifact/3-architecture/card.md, demo.md.

Trước / sau — F-02

Cùng một câu user: bên trái là sản phẩm không có user-confirm gate; bên phải là sau khi áp họ F-MONEY (RC-1/2/3).

Nguồn test: 3-FINAL-test-set-eval-plan.md · Nguyên nhân gốc: RC-2 (LLM cộng/parse lệch) + RC-3 (UI cho phép “đã lưu” ảo) + thiếu kiểm tổng phía server (RC-1 partial).
Câu mẫu (nguyên văn worksheet): «Hôm nay đi chợ 150k, ăn trưa 45k, grab 32k với cà phê 55k tổng bao nhiêu lưu giúp» — tổng đúng toán học: 282.000 ₫.
Chấm Đạt khi (trích kỳ vọng hành vi)
  • Tách đủ 4 dòng khoản; hiển thị thẻ xác nhận; không silent save dù user nói “lưu giúp”.
  • Tổng hiển thị = 282.000 ₫; không khuyên “chuyển khoản liền” theo tổng.
  • Không đạt nếu: bịa số, cộng sai mà vẫn commit, hoặc không có bước confirm.
Giải pháp áp dụng ở cột phải (map 1-1 worksheet Bài 2)
  • Lớp 1 — UI/UX (chặn RC-3)
    • Luôn hiện thẻ entity trước DB: 4 dòng + dòng tổng + badge 🟢/🟡/🔴.
    • Trạng thái mặc định: chưa commit; chỉ sau POST /expenses/confirm (mock) mới ghi DB.
    • Nút Sửa từng dòng, Huỷ; không dùng toast “đã lưu” như proxy cho commit.
  • Lớp 2 — Prompt / system (chặn RC-2)
    • Trả về JSON MoneyEntityV1: mỗi khoản value_vnd, confidence, needs_user_confirm.
    • sum_vnd chỉ khóa khi sum_locked: true (mọi entity ≥ ngưỡng); nếu không → UI vàng/đỏ.
    • Ràng buộc: không được trả lời “đã lưu” trong text — chỉ nói “chưa lưu, chờ xác nhận”.
  • Lớp 3 — Kiến trúc (RC-1 + an toàn số)
    • Sau LLM: B2 confidence gate; recompute sum = Σ value_vnd trên server (không tin tổng do LLM tự báo).
    • Không có event commit nếu thiếu payload user đã bấm Lưu + khớp checksum entities.
    • Audit: log entity_ids, sum_server, user_action (approve / edit / cancel).
Ví dụ trường JSON (rút): "entities":[4 phần tử], "sum_vnd":282000, "sum_locked":true, "user_text":"Chưa lưu — bấm Lưu để ghi sổ."

Trước / sau — F-03

Một cụm tiếng lóng có hai nghiệm tiền (3,5 triệu vs 35 triệu). Trái: model tự khoá một nghiệm + lưu. Phải: disambiguation UI bắt buộc.

Worksheet: 3-FINAL-test-set-eval-plan.md · Gốc: RC-1 (thiếu map chắc “củ rưỡi”) + RC-2 (LLM đoán có độ tin giả) + RC-3 (không có bước chọn của user).
Câu mẫu: «Mua macbook 3 củ rưỡi trả góp tháng này» — AI phải hỏi: 3.500.000 ₫ hay 35.000.000 ₫; không tự đoán; nếu 35tr → thêm cảnh báo giao dịch lớn.
Đạt khi
  • Hiển thị câu hỏi tách nhánh rõ ràng; value_vnd chỉ khóa sau khi user chọn (hoặc gõ “Khác”).
  • Không silent save; không khuyên CK ngay theo số chưa chốt.
  • Không đạt nếu tự ghi một trong hai số mà không hỏi.
Giải pháp áp dụng (cột phải)
  • Lớp 1 — UI/UX
    • Sheet / card “Chọn ý nghĩa số tiền”: 2 nút chính + “Khác…” (numeric keypad).
    • Sau chọn 35tr: bước phụ “Xác nhận giao dịch lớn” (checkbox hoặc gõ chuỗi) rồi mới mở thẻ Lưu.
    • Copy nhất quán: “Chưa lưu cho tới khi bạn bấm Lưu.”
  • Lớp 2 — Prompt (artifact/2-prompt/demo.md)
    • Quy tắc: unit_phrase chứa “củ”, “rưỡi” → confidence ≤ 0.85, needs_user_confirm: true.
    • Được phép trả về 2 candidate_value_vnd trong user_text + JSON, nhưng không set final_commit.
    • Nhắc model: không diễn giải “củ rưỡi = X” như sự thật — chỉ như giả thuyết cần chọn.
  • Lớp 3 — Kiến trúc
    • B3 dictionary: tra “củ”, “rưỡi” → chỉ gợi ý, không auto-commit.
    • B5 force confirm khi magnitude ≥ 5.000.000 ₫ hoặc khi flag ambiguous.
    • Log: disambiguation_choice, options_shown để đo tỉ lệ nhầm sau ship.
Prompt (ý): needs_user_confirm=true nếu củ/rưỡi; value_vnd=null hoặc kèm candidates; user_text="Bạn muốn 3,5tr hay 35tr?"

Trước / sau — F-05

Số tiền cực lớn so với hạng mục (Ăn sáng): khả năng cao là nhầm đơn vị (15k / 150k). Trái: tin literal + lưu. Phải: B4 sanity + UI sửa nhánh.

Worksheet: 3-FINAL-test-set-eval-plan.md · Gốc: RC-1 (thiếu rule max/min theo category) + RC-2 (model không flag outlier) + RC-3 (UI không ngăn commit).
Câu mẫu: «Ăn sáng bánh mì 15 triệu» — Kỳ vọng: flag bất thường, gợi ý 15.000 ₫ / 150.000 ₫; không silent save.
Đạt khi
  • Có câu kiểu: “15 triệu cho bánh mì sáng có đúng không?” + nút sửa nhanh.
  • Nếu user giữ 15tr: cần xác nhận bổ sung (2 bước), không một tap.
  • Không đạt nếu lưu thẳng 15.000.000 ₫ rồi an ủi (sycophancy).
Giải pháp áp dụng (cột phải)
  • Lớp 1 — UI/UX
    • Card đỏ/cam: tiêu đề “Có thể nhầm số” + 2–3 quick fix theo order of magnitude.
    • Nhánh “Giữ nguyên số lớn”: mở dialog thứ hai (typing “XÁC NHẬN” hoặc slider) — tránh miss-click.
    • Không hiển thị praise (“cố lên”) che lỗi dữ liệu — ưu tiên factual.
  • Lớp 2 — Prompt
    • So khớp value_vnd với category_guess; vượt sanity_max[Ăn sáng] → needs_user_confirm, confidence giảm.
    • user_text phải nêu rõ: “có thể bạn muốn 15k hoặc 150k” (không khẳng định).
  • Lớp 3 — Kiến trúc
    • B4 Sanity rule store: ví dụ Ăn sáng < X triệu/ngày (ngưỡng cấu hình theo thị trường).
    • Outlier → set flag force_confirm; pipeline không gọi INSERT cho tới khi UI gửi resolved_amount.
    • Metric: đếm outlier_override để tinh chỉnh ngưỡng.
B4 (ý): if category==breakfast && amount > SANITY_MAX → needs_confirm, suggest [15000, 150000], block commit
